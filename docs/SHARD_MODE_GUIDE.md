# 子GAS分散（SHARD_MODE）運用手順書

対象: 美作市教育委員会 ICT担当（システム管理者）
版数: 拡張機能 1.6.4 / バックエンド `gas/Code.gs`

---

## 0. この機能は「いつ必要か」

**通常は不要です。既定は `SHARD_MODE = false`（1校1GAS）で、従来と完全に同じ動作をします。**

必要になるのは、**1つのGASで受ける負荷が Apps Script の上限に近づいたとき**だけです。

### 0-1. 実際の上限（ここを誤解しないこと）

| 項目 | 上限 | 補足 |
|---|---|---|
| **同時実行数（ユーザーあたり）** | **30** | これが本当の壁 |
| 同時実行数（スクリプトあたり） | 1,000 | 通常は到達しない |
| 1回の実行時間 | 6分 | Web アプリの1リクエストは通常 0.1〜0.5秒 |
| トリガー合計実行時間 | 90分/日（個人） / 6時間/日（Workspace） | **時間主導トリガーのみ**。Web アプリは対象外 |

> **「1日60分」という制限は存在しません。** Web アプリ（`doPost`）はトリガー実行時間の枠を消費しません。

### 0-2. 負荷の目安

端末は稼働中 1.5 秒ごとにハートビートを送ります。

| 規模 | 毎秒のリクエスト | 1実行200ms想定の同時数 | 判定 |
|---|---|---|---|
| 1クラス 40台 | 約 27 回/秒 | 約 5.3 | 問題なし |
| 1学年 80台 | 約 53 回/秒 | 約 10.7 | 問題なし |
| **1校 240台** | **約 160 回/秒** | **約 32** | **30 を超える＝要分散** |
| 1校 240台（3〜5ms化後） | 約 160 回/秒 | 約 0.8 | 問題なし |

**まず CacheService 最適化（実装済み）で足りるか確認してください。**
`processHeartbeat` はシート全読みをせず、キャッシュから 3〜5ms で応答します。
この状態で 240 台が収まるなら、**SHARD_MODE は不要**です。実行ログで実測してから判断してください。

### 0-3. 分散の構成

```
                    ┌──────────────────────────┐
                    │  親GAS（ハブ）            │
   教員コンソール ──▶│  ・教員ログイン/権限      │
   （この1画面のみ） │  ・端末一覧の「正」       │
                    │  ・ロック/規制/配信の「正」│
                    └────────┬─────────────────┘
                             │ クラス→子URLを返す／指示を伝達（fetchAllで並列）
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        ┌──────────┐   ┌──────────┐   ┌──────────┐
        │ 子GAS A  │   │ 子GAS B  │   │ 子GAS C  │
        │ 5年1組   │   │ 5年2組   │   │ 6年1組   │
        └────▲─────┘   └────▲─────┘   └────▲─────┘
             │              │              │
          児童端末       児童端末       児童端末
        （1.5秒ごと）   （1.5秒ごと）   （1.5秒ごと）
```

**教員は親コンソールしか見ません。** 子GASの存在は教員からは見えません（「完全1画面」）。

## 1. 用語と保存場所

| 名前 | 保存先 | 内容 |
|---|---|---|
| `SHARD_MODE` | `Code.gs` の `CONFIG` | `true` でこのスクリプトが**親**になる |
| `SHARD_CHILD_MODE` | `Code.gs` の `CONFIG` | `true` でこのスクリプトが**子**になる |
| `SHARD_MAP_V1` | スクリプトプロパティ | クラス名 → 子GAS URL の対応表（JSON） |
| `SHARD_DEFAULT_URL` | スクリプトプロパティ | クラス不明時の受け皿となる子GAS URL（任意） |
| `SHARD_SECRET` | スクリプトプロパティ | 親⇔子の共有シークレット（`sk_` で始まる） |

いずれも **GAS の「プロジェクトの設定」→「スクリプト プロパティ」** に入れます。
スプレッドシートのセルではありません。

## 2. 導入手順（全体像）

作業順序を間違えると**全校の端末が通信できなくなります**。次の順で進めてください。

1. 子GASを必要数デプロイする（**先に子**）
2. 共有シークレットを生成し、全子GASへ設定する
3. 親GASにマッピングを設定する
4. 親GASを `SHARD_MODE = true` にする
5. 端末1台で動作確認 → 全校展開

> **順序が重要な理由:** 親を先に `SHARD_MODE = true` にすると、子GASが未準備のまま
> 端末に「存在しない子GASのURL」を配ってしまい、端末が通信できなくなります。

## 3. 子GASの準備

### 3-1. 子GASを何個作るか

**1クラス＝1子GAS** を基本とします。上限は 1クラス 40台です。

- 5年1組・5年2組・6年1組 … のように**クラス数だけ**用意する
- 目安: 1校あたり 6〜12 個
- 増やすときは、子GASを追加してマッピングに1行足すだけ（親の再デプロイ不要）

**同じ子GASを複数クラスで共有しても構いません。** 負荷が分散できていれば十分です。

### 3-2. 子GASの作成

1. 子GAS用のスプレッドシートを新規作成する
2. 「拡張機能」→「Apps Script」を開く
3. `gas/Code.gs` の内容を**そのまま全部**貼り付ける（親と同じファイル）
4. `CONFIG` の該当行だけ書き換える

```js
// 子GASではこうする
SHARD_MODE: false,        // ← 子は親ではない
SHARD_CHILD_MODE: true,   // ← これを true にする
```

5. 保存（Ctrl+S）
6. 「デプロイ」→「新しいデプロイ」→ 種類「ウェブアプリ」
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員**（または組織内）
7. 表示された **ウェブアプリのURL**（`.../exec` で終わる）を控える

> **子GASのURLは「新しいデプロイ」で構いません。** 端末が直接使うのは親のURLだけです。
> 子のURLは親のマッピングに書くので、差し替えも容易です。

### 3-3. 子GASのシート構成

子GASのスプレッドシートにも**端末一覧シートが必要**です。
`gas/Code.gs` を貼って保存すれば、初回アクセス時にヘッダーが自動作成されます。

子のシートには「その子へハートビートした端末」だけが並びます。
**児童の行が無くても一括操作は失敗しません**（親が指示と同時に行を作ります）。

## 4. 共有シークレット（`sk_`）の設定

親と子は**教員トークンではなく共有シークレット**で認証します。
シークレットが一致しない子は、親からの指示を**一切受け付けません**（安全側）。

### 4-1. シークレットを生成する

**親GASのスクリプトエディタ**で、次の関数を1回だけ実行します。

```js
function generateShardSecretForSetup() {
  const s = getOrCreateShardSecret();
  Logger.log('SHARD_SECRET = ' + s);
}
```

1. エディタ上部の関数選択で `generateShardSecretForSetup` を選ぶ
2. 「実行」
3. 「実行ログ」に `SHARD_SECRET = sk_xxxxxxxxxxxxxxxx` と出る
4. この値を**全子GASに同じものを設定**する

> 生成は冪等です。2回実行しても値は変わりません。
> **値を変えたいときだけ**、後述の「シークレット再発行」を行います。

### 4-2. 子GASへ設定する

各子GASの「プロジェクトの設定」→「スクリプト プロパティ」で:

| プロパティ | 値 | 必須 |
|---|---|---|
| `SHARD_SECRET` | `sk_xxxxxxxxxxxxxxxx`（親と同一） | **必須** |
| `SHARD_CHILD_MODE` | `true` | **必須** |
| `SHARD_PARENT_URL` | 親GASのデプロイURL（`.../exec`） | **必須**（下記 4-3） |
| `SPREADSHEET_ID` | この子GASが書き込む子スプレッドシートのID | 推奨 |

> `SPREADSHEET_ID` を省くと、コード内の既定値（親のシートID）が使われます。
> **子GASでは必ず設定してください。** 設定しないと親のシートへ書き込んでしまいます。

### 4-3. 子が親へ「この児童は誰か」を聞く仕組み（`SHARD_PARENT_URL`）

子GASは**名簿を持ちません**（子のシートには、その子へハートビートした端末の行しかない）。
そのため、クラスが分からない端末が子GASへ来ると、次のような**鶏卵問題**が起きます。

```
端末 ──▶ 子GAS（クラス未取得のまま到着）
          │  名簿が無いのでクラス＝「未設定」で登録
          │  class_name が空 → assigned_gas_url を返せない
          ▼
        端末は通信先を切り替えられず、永久にクラスを学習できない
```

これを解消するため、子GASは `SHARD_PARENT_URL` の親へ **`shard_lookup`** を送り、
氏名・学校名・**クラス**を教えてもらいます（結果は10分キャッシュ）。

```
端末 ──▶ 子GAS ──▶ 親GAS（shard_lookup / SHARD_SECRET 認証）
                    │  端末一覧から児童IDで検索（表記ゆれ吸収）
                    ▼  氏名・学校名・クラス＋assigned_gas_url を返す
          ◀────────┘
          │  子シートの A〜D 列を埋める
          ▼
        応答の class_name が「5年1組」になる
          ▼
        端末が assigned_gas_url を受け取り、正しい子GASへ切り替わる
```

| 項目 | 内容 |
|---|---|
| 送信元 | 子GAS |
| 送信先 | `SHARD_PARENT_URL`（親GAS） |
| 認証 | `SHARD_SECRET`（不一致は `unauthorized`） |
| キャッシュ | 見つかった=10分／見つからない=1分 |
| 親URL未設定時 | 照会しない（従来動作のまま。例外は出さない） |

> **`SHARD_PARENT_URL` を設定しないと、この救済は働きません。**
> `SHARD_MAP_V1` に空キー `""`（既定ルーティング）を入れている運用では**必須**です。

### 4-4. シークレット再発行（漏洩時のみ）

親GASで:

```js
function rotateShardSecretForSetup() {
  PropertiesService.getScriptProperties().deleteProperty('SHARD_SECRET');
  const s = getOrCreateShardSecret();
  Logger.log('新しい SHARD_SECRET = ' + s);
  invalidateShardConfig();
}
```

実行後、**全子GASに新しい値を設定し直してください。**
再発行すると、旧シークレットの子は指示を受け取れなくなります。

## 5. マッピングテーブルの設定

### 5-1. 記述例（親GASのスクリプトプロパティ）

`SHARD_MAP_V1` に**JSON文字列**を入れます（1行で構いません）。

```json
{
  "5年1組": "https://script.google.com/macros/s/AKfycb...AAA/exec",
  "5年2組": "https://script.google.com/macros/s/AKfycb...BBB/exec",
  "6年1組": "https://script.google.com/macros/s/AKfycb...CCC/exec",
  "6年2組": "https://script.google.com/macros/s/AKfycb...DDD/exec"
}
```

**クラス名だけ**を書きます。学校名は含めません（親GASは1校＝1つです）。

### 5-2. 表記ゆれは自動で吸収されます

次の書き方はすべて同じクラスとして扱われます。

| 書いた表記 | 内部キー |
|---|---|
| `5年1組` | `5-1` |
| `５年１組`（全角） | `5-1` |
| `5-1` | `5-1` |
| `5/1` | `5-1` |
| `5年 1組`（空白入り） | `5-1` |
| `5組` | `5-1` |

端末一覧シートの「クラス」列が `5年1組` でも `５年１組` でも、
`5-1` に対応する子GASへ振り分けられます。

> `未設定` はどの子GASにも割り当てられません。
> クラス未設定の児童は親GASが受け持ちます（または `SHARD_DEFAULT_URL` へ）。

### 5-3. 既定URL（任意）

`SHARD_DEFAULT_URL` に子GASのURLを入れると、
**マッピングに無いクラスの児童もその子GASへ**回せます。

```
SHARD_DEFAULT_URL = https://script.google.com/macros/s/AKfycb...ZZZ/exec
```

- 入れない場合: マッピングに無いクラスは親GASが受け持ちます
- 入れる場合: クラス不明の児童も子へ分散されます

> **専科教員の取得が速くなる仕組み:** 対象クラスが1つだけの教員（専科など）は、
> **そのクラスを担当する子GASにだけ**問い合わせます。1クラス分の通信時間で済みます。
> このとき `SHARD_DEFAULT_URL` は取りこぼし防止のため常に対象に含まれます。

### 5-4. 設定の確認（管理API）

管理者でログインした状態で、次のアクションを叩くと現在の設定が見えます。

```json
{ "action": "get_shard_settings" }
```

返る内容（シークレットは伏字）:

```json
{
  "success": true,
  "settings": {
    "shard_mode": true,
    "child_mode": false,
    "classes": [
      { "class_name": "5年1組", "normalized": "5-1", "url": "https://.../exec" }
    ],
    "normalized_count": 4,
    "default_url": "",
    "secret_configured": true,
    "max_per_class": 40
  },
  "is_admin": true
}
```

保存もAPIで可能です（管理画面に設定UIは**設けていません**。教員画面を簡潔に保つため）。

```json
{
  "action": "save_shard_settings",
  "settings": {
    "classes": [
      { "class_name": "5年1組", "url": "https://.../exec" },
      { "class_name": "5年2組", "url": "https://.../exec" }
    ],
    "default_url": ""
  }
}
```

> URL は `http://` または `https://` で始まる必要があります。それ以外は拒否されます。

## 6. `SHARD_MODE = true` への切り替え

### 6-1. 前提チェック（重要）

切り替える前に、必ず確認してください。

- [ ] 子GASをすべてデプロイした
- [ ] 全子GASに `SHARD_CHILD_MODE = true` を入れた
- [ ] 全子GASに**同じ** `SHARD_SECRET` を入れた
- [ ] `SHARD_MAP_V1` のJSONが正しくパースできる（`get_shard_settings` で確認）
- [ ] 子GASのURLがすべて `.../exec` である

### 6-2. 切り替え

親GASの `Code.gs` を1行だけ変更します。

```js
// 変更前
SHARD_MODE: false,

// 変更後
SHARD_MODE: true,
```

### 6-3. 再デプロイ（**必ず既存デプロイを更新**）

1. 「デプロイ」→「**デプロイを管理**」
2. 使用中のデプロイの**鉛筆アイコン（編集）**をクリック
3. バージョンで「新バージョン」を選ぶ
4. 「デプロイ」

> ### 絶対に「新しいデプロイ」を押さないでください
> 新しいデプロイは**URLが変わります**。URLが変わると、全校の端末に配布済みの
> 管理ポリシー（`gas_url_map`）がすべて無効になり、**全校の端末が通信できなくなります。**
> 復旧には全校のポリシー再配布が必要です。

### 6-4. 動作確認

1. 端末1台で拡張機能の動作を確認（最終同期日時が更新されるか）
2. 教員コンソールで端末一覧が表示されるか
3. 一括ロックが1クラスで効くか
4. 問題なければ全校展開

## 7. 動作の仕組み（運用時に知っておくと役立つ点）

### 7-1. 端末側の通信先の切り替え

| タイミング | 端末の動き |
|---|---|
| 初回 | 親GASへハートビート → 応答に `assigned_gas_url` が入る |
| 2回目以降 | **子GASへ直接**ハートビート（1.5秒周期を維持） |
| 6時間ごと | 親へ再確認（クラス変更に追従） |
| 子へ3回連続失敗 | **親へ自動切り戻し**（端末が孤立しない） |
| 切り戻し後30分 | 再割り当てを保留（壊れた子との無限往復を防ぐ） |

端末側の保存先は `chrome.storage.local` です（管理ポリシーではありません）。
そのため**端末ごとに個別の設定作業は不要**です。

### 7-2. 教員コンソールの取得（`get_all`）

| 場面 | 動き |
|---|---|
| 単一クラス選択 | **クライアント側で絞り込み**。サーバー再取得なし（瞬時に切り替わる） |
| 全校・全学年 | 必要な子GASへ **`fetchAll` で並列**取得（12クラスでも待ち時間は1回分） |
| 専科教員（対象クラス1つ） | **該当する子GASにだけ**問い合わせ（最も速い） |
| 連続操作・自動更新 | **4秒キャッシュ**に当たる（子GASへの再通信なし） |

キャッシュは `dev_v`（書き込み版数）をキーに含めています。
ロック・配信・規制などの**書き込みをすると自動的に失効**するため、
操作直後に古い一覧が表示されることはありません。

集約の経路は `get_all`（`doPost`）と `api_getAllDevices`（`google.script.run`）の
2つがありますが、**どちらも同じ集約処理（`getShardMergedDevices`）を通ります**。
以前は `api_getAllDevices` だけが親シートを直読みしていたため、
画面の開き方によって子の端末が見えたり見えなかったりしました（現在は統一済み）。

#### 親と子の突き合わせ（split-brain の解消）

端末は割り当て後**子GASにしかハートビートしません**。そのため子のシートだけが更新され、
親のシートの「最終同期日時」は切り替えた時点で止まります。
同じ児童の行が親と子の両方に存在する状態（二重管理）を、取得時に**1台ずつ突き合わせて統合**します。

| 項目 | どちらを正とするか |
|---|---|
| 氏名・学校・クラス | **親が正**。親が「未設定」「未登録児童…」「〜(Googleアカウント)」のときだけ子で補う |
| 最終同期日時・現在URL・画面情報・監視状態 | **最終同期が新しい方**（通常は子） |
| `is_online` | **統合後の最終同期から再計算**（親だけ見ると誤判定する） |
| ロック・URL規制・一斉配信・画面要求・備考 | **親が正**。親が空で子に入っていれば子の値を残す（伝達済みの値を消さない） |

> **以前の症状**: 「画面ロックを押した瞬間にオフライン表示になる」のは、
> 親に居る児童の子の行を**捨てていた**ため、止まった親の日時だけで
> `is_online = false` と判定していたことが原因でした（現在は統合して解消）。
> 同じ理由で、ロック直後に `dev_v` が進んでキャッシュが失効し、
> その瞬間に古い日時が露出していました。

### 7-3. 教員コンソールの稼働状態（`ka_active`）の伝達

端末は「教員コンソールが起動中」のときだけ 1.5 秒周期で同期します。
教員は親コンソールにしかログインしないため、**親が子へ稼働状態を配ります**。

- 稼働中（`true`）: **30秒に1回**へ間引き
- 解放（`false`）: **即時**

これが無いと、子GASは永久に「非稼働」と判断し、**分散した瞬間に全端末が同期停止**します。

### 7-4. 全校一括操作

「全校一括ロック」「全校一括URL配信」も、親から全子GASへ
**`fetchAll` で一斉に**伝達します（1回分の待ち時間）。

子のシートに対象児童の行が無い場合は、**指示と同時に行を作ってから**適用します。
行の作成に失敗した場合は、応答の `ensure_error` に理由が入り、
コンソールの操作結果から確認できます（**無言で失敗しません**）。

### 7-5. 操作の入口は2つある（両方から子へ伝達します）

教員コンソールは、画面の状態によって **`google.script.run`** と
**`doPost`（`fetch`）** の2つの入口を使い分けます。
**どちらの入口から操作しても、子GASへ同じ内容が伝達されます。**

| 操作 | `google.script.run` 経由 | `doPost` 経由 |
|---|---|---|
| 画面ロック | `api_bulkLock` | `bulk_lock` |
| 一斉URL配信 | `api_bulkBroadcast` | `bulk_broadcast` |
| URL規制 | `api_bulkFilter` | `bulk_filter` |
| 個別更新 | `api_updateSingle` | `update_single` |
| コンソール稼働 | `api_consoleTouch` / `api_consoleRelease` | `console_touch` / `console_release` |

> **以前の症状**: 「画面ロックを押しても端末に届かない」「同期周期：停止（猶予20秒）から
> 戻らない」は、上表の **`google.script.run` 側だけが子へ伝達していなかった**ためでした。
> 教員コンソールは `google.script.run` を優先するので、`doPost` 側だけ正しくても
> 実際の操作は届いていませんでした（現在は両方から伝達します）。

## 8. トラブルシューティング

### 8-1. 端末が同期しない

| 症状 | 確認すること |
|---|---|
| 全校で同期しない | 親GASのURLが変わっていないか（「新しいデプロイ」を押していないか） |
| 特定クラスだけ同期しない | そのクラスの子GASがデプロイされているか、URLが正しいか |
| 分散直後に止まった | 子GASの `SHARD_CHILD_MODE = true` になっているか |
| 子へ切り替わった直後に止まる | `SHARD_SECRET` が親子で一致しているか |

### 8-2. 教員コンソールに児童が出ない

- `SHARD_MAP_V1` のJSONが壊れていないか（`get_shard_settings` で確認）
- 子GASが「アクセスできるユーザー: 全員」になっているか
  （制限されていると親からの `fetchAll` が 302 でログイン画面を返し、JSONパースに失敗します）

### 8-3. 一括ロックが効かない

- `get_shard_settings` で `secret_configured: true` か
- 子GASの実行ログに `unauthorized` が出ていないか
- 応答の `shard` フィールドに `ensure_error` が出ていないか

### 8-4. 動作が遅い

- 実行ログで `get_all` の実行時間を確認（4秒キャッシュが効いていれば 100〜200ms）
- 子GASの数が多すぎないか（1校 6〜12 個が目安）
- 子GAS側の `processHeartbeat` が 3〜5ms で応答しているか

### 8-5. 子シートのクラス・氏名が空（または「未設定」）になる

**症状**: 子スプレッドシートの「端末一覧」で、A〜D列（児童ID・学校名・氏名・クラス）が
空、または氏名が「1607002 (Googleアカウント)」・クラスが「未設定」のまま。
その結果 `assigned_gas_url` が返らず、端末の通信先が親のまま固定される。

**原因**: 子GASは名簿を持たないため、クラス未取得の端末が来ると
「未設定」で登録してしまい、以後もクラスを学習できない（鶏卵問題）。

**対処**:
1. 各**子GAS**に `SHARD_PARENT_URL`（親の `/exec`）が入っているか確認する
2. 各**子GAS**に `SHARD_SECRET`（親と同一）が入っているか確認する
3. 子GASで次を実行し、`found=true` と `class_name` が返るか確認する

```js
function testChildLookup() {
  const r = shardLookupFromParent('1607002@city-mimasaka.ed.jp');
  Logger.log(JSON.stringify(r));
}
```

4. `found=false` の場合は**親の端末一覧**にその児童IDが登録されているか確認する
   （児童IDの照合は空白・大文字小文字・全角半角を吸収しますが、
   そもそも行が無ければ見つかりません）
5. 親側で確認する場合:

```js
function testParentLookup() {
  Logger.log(JSON.stringify(findStudentById('1607002@city-mimasaka.ed.jp')));
}
```

既に「未設定」で登録済みの行は、次回のハートビート時に自動で補完されます
（`hbApplyChildIdentity` が不足している列だけを書きます。教員が手で直した値は上書きしません）。

### 8-6. 行がずれて空行に書き込まれる（K・L列だけ更新される）

**症状**

- 子スプレッドシートで、既存の児童行（例: 2行目）が更新されない
- その代わりに**A〜D列が空欄の行**が作られ、K列（現在開いているURL）と
  L列（最終同期日時）だけが書き込まれる
- 管理画面では対象端末が「オフライン」と表示される（`is_online: false`）
- そのとき `getLastRow()` が実際の児童数より大きい（例: 児童1人なのに 3）

**原因**

ハートビートのたびに「その児童が何行目か」を毎回引き直すのではなく、
**行番号をキャッシュに保持していた**ことです。

| 何が起きていたか | 詳細 |
|---|---|
| 行番号を最大6時間キャッシュ | 児童ごとに「2行目」等の行番号を保持していた |
| キャッシュの版数は教員操作でしか進まない | 管理画面からの書き込みでしか更新されない |
| スプレッドシートを直接編集すると検知できない | 行の削除・挿入・並べ替えをしても版数は変わらない |
| 結果として行番号だけがズレる | 2行目の児童のハートビートが3行目（空行）へ書かれる |

A〜D列が空のまま K列・L列だけが書かれるのは、新規行の追加（全19列を書く）ではなく
**「現在URL」と「最終同期日時」の2列だけを書く処理**が、実在しない行に対して
実行された証拠です。シートはその行を自動的に用意するため、空行が増えます。

**修正内容（バックエンド修正。拡張機能の版数は据え置き）**

- 行番号のキャッシュを**廃止**しました。毎回シートを読んで児童IDから引き直します。
- ヘッダー（列の位置）も毎回読み直します。列の挿入・削除でも壊れません。
- 追加コストは「シート全体を1回読む」だけです。数百行規模では体感差はありません。
- 書き込みが不要なとき（URLも同期時刻も変化なし）は、従来どおり書きません。

**既にできてしまった空行の掃除**

修正後は、児童IDが空の行を見つけると、新規登録時に**その行を再利用**します
（新しく行を増やしません）。

ただし「A〜D列が空で、K・L列だけ値が入っている行」は、次のどちらかで消してください。

1. そのまま放置する（次の新規児童が再利用します）
2. 手動で行を削除する（削除しても、修正後は行番号を毎回引き直すので再発しません）

**実測のしかた（どの行に書いたかを確認する）**

`gas/Code.gs` の先頭付近にある次の定数が `true` のとき、実行ログに `[HB]` 付きの
記録が出ます（原因調査用。落ち着いたら `false` に戻してください）。

```js
const HB_DEBUG_LOG = true;
```

1. 子GASのエディタ → 「実行数」→ 該当時刻の `doPost` を開く
2. 「ログ」に次のような行が出ます

```
[HB] resolve: 一致 row=2 id=1607002@city-mimasaka.ed.jp (総行数=2, 空ID行の先頭=-1)
[HB] heartbeat: id=1607002@city-mimasaka.ed.jp -> row=2 (総行数=2)
[HB] heartbeat: 書き込み不要 row=2 elapsed=8ms
```

| ログ | 意味 |
|---|---|
| `resolve: 一致 row=N` | 児童を見つけた行番号。**ここが実際の行** |
| `resolve: 不一致` | 見つからず新規登録へ回った（ID の表記を確認） |
| `空ID行の先頭=N` | 児童IDが空の行。新規登録時に再利用される |
| `heartbeat: 2列まとめ書き row=N` | K列・L列をまとめて書いた行 |
| `heartbeat: K列書き row=N` | 現在URLだけ書いた行 |
| `heartbeat: L列書き row=N` | 最終同期日時だけ書いた行 |
| `register: 残骸行を再利用 row=N` | 空行を再利用した（新規行は増えない） |
| `register: 新規行を追加 row=N` | 本当に新しい児童だった |

**正常時の見え方**

- `resolve` の `row=` と、書き込みログの `row=` が**一致**している
- 2行目の児童なら、どちらも `row=2`
- 書き込み後、シートの L列（最終同期日時）が現在時刻になる

> **確認のポイント**: ログの `row=` が 3 なのに、シートの3行目の A列が空なら、
> まだ古いコードが動いています。**既存デプロイを更新**（鉛筆アイコン → 新バージョン）
> したか確認してください。「新しいデプロイ」を押すと URL が変わり、
> 端末のポリシー設定が無効になります。

### 8-7. 画面ロックなどを押した直後に「オフライン」と表示される

**症状**

- 画面ロック・一斉表示・URL規制を実行すると、その直後から対象端末が
  管理画面で「オフライン」になる
- ただし**端末は通信を続けている**（子GASの「実行数」に `doPost` が数秒おきに出続ける）
- **子スプレッドシート**の L列（最終同期日時）は現在時刻で更新され続ける
- **親スプレッドシート**の L列は、割り当て時点の古い値で止まっている
- 画面の「最終通信」が、時間の経過とともに「2分前 → 5分前」と増えていく

**まず確認すること（切り分け）**

| 見る場所 | 期待される状態 | 意味 |
|---|---|---|
| 子GAS「実行数」 | `doPost` が数秒おきに出続けている | 端末は止まっていない |
| 子シートの L列 | 現在時刻で更新され続けている | 子GASは正常に書いている |
| 親シートの L列 | 古い値で止まっている | **これは仕様どおり（下記）** |

**原因（2つが重なっていました）**

**① 親シートの L列が古いのは仕様です**

端末は割り当て後「子GAS」にしかハートビートしません。親シートの L列は
割り当て時点で止まるのが設計どおりの動作で、**親シートへの書き戻しは行いません**。
正しい値は「読み取り時にメモリ上で子と突き合わせる」ことで得ます。

したがって、親シートの L列が古いこと自体は異常ではありません。
問題は**その突き合わせが働かず、親の古い値だけが画面に使われていた**ことです。

**② 突き合わせが失敗しても、黙って親の値が使われていた**

子GASからの取得が次のいずれかで失敗すると、以前は**何も記録せずに**親の一覧だけを
返していました。画面には「親の古い最終同期」だけが残り、原因が分からないまま
オフライン表示になります。

| 失敗の内容 | 起きる状況 |
|---|---|
| 200 以外が返る | 共有シークレット不一致、Webアプリの公開範囲の誤り |
| 応答が JSON でない | ログイン画面の HTML が返っている（公開範囲「全員」になっていない） |
| 取得が例外になる | URL の誤り、一時的な通信失敗 |
| `data` が 0 件 | 子側の名簿・クラス解決の不整合 |

さらに、シートの日時 `"2026/11/02 11:19:32"` を `new Date()` に任せて解釈していたため、
**GAS のスクリプトタイムゾーンが変わると判定結果が反転**しました。
実測では同じデータ・同じ比較時刻でも `TZ=UTC` なら `is_online=true`、
`TZ=Asia/Tokyo` なら `is_online=false` になりました。

**修正内容（バックエンド修正。拡張機能の版数は据え置き）**

- シート日時の解釈を `sheetTsToMs()` に一本化しました。
  日本時間（UTC+9）として組み立てるため、**実行環境のタイムゾーンに依存しません**。
- 子GASの取得失敗を `_diag` に記録するようにしました（非200／JSONでない／0件）。
- 子が1台も返さなかったときは、実行ログに理由を出します（`HB_DEBUG_LOG = true` のとき）。
- 統合結果に `last_seen_source`（`child` / `parent` / `none`）を付けました。
  **どちらの値で判定したか**が分かります。
- 親シートへの書き戻しは**行いません**（設計どおり読み取り時集約のみ）。

**実測のしかた**

`HB_DEBUG_LOG = true` のとき、親GASの実行ログに次のどちらかが出ます。

```
[HB] shard: 子GASから取得できません [{"url":"https://...","status":401}]（この児童は親シートの古い最終同期で判定されます）
```

→ 子GASに届いていません。**共有シークレット**と**Webアプリの公開範囲**を確認してください。

出ない場合は子GASから取得できています。応答の `last_seen_source` を見てください。

| `last_seen_source` | 意味 |
|---|---|
| `child` | 子の最新値で判定（正常） |
| `parent` | 親の方が新しい（割り当て直後など） |
| `none` | どちらにも日時が無い（未同期の端末） |

**正常時の見え方**

- 子シートの L列が更新され続けている
- 親コンソールの「最終通信」が「数秒前」で維持される
- 画面ロックを押しても「オフライン」に落ちない

> **確認のポイント**: 直らない場合は、まず子GASの「実行数」で `doPost` が
> 続いているかを見てください。止まっていれば端末側、続いていれば親側の集約の問題です。
> どちらの場合も**既存デプロイを更新**（鉛筆アイコン → 新バージョン）したか確認してください。

### 8-8. 元に戻したい（分散をやめる）

1. 親GASの `SHARD_MODE` を `false` に戻す
2. **既存デプロイを更新**（鉛筆アイコン → 新バージョン）
3. 端末は6時間以内に自動で親へ戻ります
   （すぐ戻したい場合は、端末の `chrome.storage.local` を消すか、翌朝の再起動を待つ）

> `SHARD_MAP_V1` を消すだけでも、親が割り当てを返さなくなるため端末は親へ戻ります。

### 10-2. 名簿照会・ID照合の関数

| 関数 | 役割 | 動作する側 |
